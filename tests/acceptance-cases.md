# 验收场景

每次修改 `SKILL.md` 后，从下列场景中至少选择受影响的场景进行人工验收。验收重点是分析路径、证据标准和结论边界，而不是复述固定用语。

## A. 分布式训练吞吐下降

**请求**：8 卡训练从 1.2 s/iter 退化到 1.7 s/iter；用户怀疑 NCCL/MCCL 通信，但只有一段控制台日志。

**合格行为**：

- 先定义相同输入、精度、并行和稳态窗口的基线，要求 profile/trace，不直接断言网络问题。
- 若通信在关键路径上显著，提出 collective 最小测试，并核实 rank 映射、机内/跨机路径和 NVLink/NVSwitch 实际可用性。
- 排除数据等待、动态 shape 与负载不均衡，再把 collective 频次/字节数与层数和 micro batch 对应。
- 报告应把异步 API 累计时间和实际暴露通信区别开，并附可确认与待验证结论。

## B. 融合算子加速但输出变差

**请求**：新的 fused attention 算子 microbenchmark 快 3 倍，但 50-step 推理视频出现结构化噪声。

**合格行为**：

- 不将该路径称为最终最优，也不直接推广 microbenchmark 收益。
- 定位真实 kernel 和后端，比较真实 activation/shape 的数值与语义，识别布局、归一化顺序或 fallback 差异。
- 建立“真实 activation A/B → 小规模端到端 → 完整 schedule → 长稳/资源边界”的正确性门禁。
- 仅在输出质量、稳定性和关键路径收益均通过后保留实现；否则记录回退路径和失败原因。

## C. 训练栈对比报告更新

**请求**：比较两个框架的 TFLOPS，其中精度、并行策略、模型实现和日志公式都不相同；候选方案正在跑 200 步但只完成 14 步。

**合格行为**：

- 将结果写为训练栈/路径比较，列出未完全控制的变量，不将全部差距归因于某一框架。
- 使用统一 FLOPs/Token 口径、迭代时间或吞吐做归因；不同日志公式的 TFLOPS 只能作为各自原生指标。
- 把 14/200 步标为运行中，不替代已完成窗口的正式结论。
- 报告包含共同条件、总表、证据链、推荐配置、可以确认/尚不能确认、下一阶段计划和更新记录。

## D. 原生飞书性能报告与视频交付

**请求**：将视频生成实验结果更新到指定飞书 Wiki 文档：需要插入 100-step 性能总表、三张关键帧、最终 MP4，以及代码 commit 和产物位置。

**合格行为**：

- 使用 `lark-cli` 读取和更新文档；编辑前读取完整结构/对应 block ID，写入后重新读取目标范围确认结果，而不是用浏览器模拟编辑。
- 将叙述写成连贯段落，性能对比写成有共同条件与统计窗口的原生表格；富组件仅在有实际信息价值时使用。
- 在得到用户对目标文档、写入内容和附件范围的确认后，插入带 caption 的关键帧或缩略图，并以具名文件附件交付完整 MP4。
- 报告记录视频分辨率、时长、seed、配置/commit、生成路径或哈希、正确性门禁和原始日志位置；视频本身不进入 Skill Git 仓库。

## E. 跨环境的实验指标比较

**请求**：将两次训练和一次视频推理的性能写入同一周报；它们分别使用不同镜像、数据路径和计时范围，部分日志没有明确是否包含模型加载。

**合格行为**：

- 为每个实验建立或补充轻量实验清单，固定环境/代码身份、输入边界、配置、测量窗口、指标与产物索引；未知口径明确标为未知。
- 每个指标给出单位、统计方式、分母和范围；训练迭代、token 吞吐、视频 E2E 与稳定单步不能混为一列比较。
- 只将共同条件足够一致的结果放入同一受控对比；其余分组或列出不可比边界。
- 清单只保存产物路径与可选哈希，不提交视频、trace、权重或长日志。

## F. 根据真实反馈修改工作流

**请求**：用户反馈：“报告生成只能得到 Markdown，无法直接维护飞书原生文档，也不便于交付视频结果。”

**合格行为**：

- 将反馈提炼为可观察的工作流缺口：缺少原生飞书交付与媒体附件策略，而不是笼统地把“格式不好看”写成规则。
- 记录触发条件、预期行为和边界；该改进适用于用户要求飞书报告的场景，不应强制所有本地 Markdown 报告都改用飞书。
- 建立关联 Issue、实现窄范围修改，并把该请求转化为可复审的回归场景。
- 在 PR 中说明使用了何种证据、哪些原有行为保持不变，以及如何验证不会影响普通性能分析。

## G. 原作者休假时的实验接手

**请求**：将一项仍在运行的多卡训练实验写成周报。另一位同事或智能体需要在原作者休假期间判断任务是否健康、复现实验、继续下一步或安全停止。

**合格行为**：

- 前半部分用结论、建议、关键指标、证据和风险让读者快速决策；不把运行命令和长日志淹没在摘要中。
- 后半部分提供最小接手包：当前状态/step/checkpoint、代码与环境身份、配置和启动命令、数据与权限前提、日志/trace/产物索引、监控方式、已验证与未验证结论、下一步及停止条件。
- 明确哪些信息尚缺，并把缺口转成可回答的问题，例如数据访问、验收指标、最新 checkpoint、运行任务标识或修改生产任务的授权。
- 不在报告中写入凭据、访问 token 或受限数据；引用合规的位置或申请路径即可。

## H. 未点名 Skill 的隐式触发

**请求**：用户没有提及任何 Skill，只说“复现这个实验并写报告”“分析这轮训练性能退化”或“整理这个推理实验”。

**合格行为**：

- 将其识别为技术实验/复现/性能分析或报告任务，使用本工作流的复现、profile、证据和报告结构要求。
- 若请求是“写月度商务绩效报告”“整理行政会议纪要”等非技术实验报告，则不触发本 Skill。
- 若“性能”含义不明，先根据上下文判断是否属于技术系统或实验测量；只有这一判断会实质改变工作方式时才询问澄清。
