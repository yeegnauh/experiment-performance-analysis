# 飞书报告与媒体交付

当用户要在飞书原生报告中阅读、创建或更新实验结论时，使用 `lark-cli`。它能保留 Docx/Wiki 的结构、表格、代码块和媒体资源；不要把浏览器自动化作为常规读写方式。

## 操作顺序

1. 确认目标文档、写入范围和要上传的附件。对创建/更新、上传或移动云端内容，先取得用户授权。
2. 读取文档时，先取目录或相关章节；若需要编辑既有内容，获取完整结构、样式和 block ID。用 `docs +fetch` 的 `outline`、`section`、`range` 或 `keyword` 缩小读取范围。
3. 创建报告或写入完整章节时，默认使用原生 XML；用户提供 Markdown 文件或明确要求 Markdown 导入时才改用 Markdown。局部更新使用精确的 `docs +update` 指令，不覆盖无关章节。
4. 更新后重新读取受影响范围，核对标题、表格、代码块、资源块和链接。`overwrite`、`block_replace` 或删除后，不再使用受影响的旧 block ID。

在真正执行飞书写操作前，按当前安装版 `lark-cli` 的文档技能要求阅读其认证、XML、创建/更新和媒体插入说明；使用 `--as user` 访问个人/团队报告。

## 报告排版

- 分析、背景和结论使用连贯段落；共同条件、性能结果、配置对比和实验台账使用表格。
- 采用一套连续的标题编号。不要把只有一句说明的小项升成标题，也不要混用多套编号。
- 代码和配置用带语言与 caption 的代码块。一个结论或风险提示可以使用 callout，但不把每个段落都组件化。
- 默认朴素排版；颜色和分栏仅在表达成功/风险、短对比或关系图时使用，并保持全文语义一致。
- 保留已存在文档的结构、语气和资源；用户提供的范例文档优先于默认样式。

## 媒体与产物

### 图像

对性能图、关键帧和架构图，使用 `lark-cli docs +media-insert` 插入本地图片或剪切板图片。图片应具有简洁 caption；必要时指定显示宽度并居中。报告正文中说明该图片支持的结论及其来源，而不让图片孤立存在。

### 视频生成实验

视频附件应采用两层交付：

1. **可读预览**：在结果段落或“实验产物”章节提供关键帧、缩略图或联系表，标明用例、step/seed、分辨率、时长和验证状态。若无法生成预览图，明确说明原因，不能假装视频已核验。
2. **原始附件**：将完整 MP4 等视频作为具名文件通过 `docs +media-insert --type file` 插入到报告的“实验产物”章节或文末附件区。附件名应包含模型/用例/配置或日期，避免 `output.mp4` 等不可辨认名称。

对每个可复现实验结果，报告还应包含代码 commit/镜像身份、关键配置、输入说明、输出位置、文件大小或哈希（可用时）、原始日志/trace 位置，以及正确性或画质门禁。媒体插入成功后，记录返回的文件 token/block ID 并重新读取文档确认。

### 大型文件边界

视频、trace、activation snapshot、模型权重、缓存和长日志属于实验产物，不应提交到本 Skill Git 仓库。仓库只维护工作流、模板、验收案例和必要的小型示例；报告引用约定的云端或实验存储位置。

## 核验清单

- 报告的性能数据是否标注统计窗口、分母和是否包含加载/编译/I/O？
- 所有图、视频和附件是否有可理解的名称、caption 或上下文？
- 完整视频是否同时有预览材料，且预览与视频来自同一实验结果？
- 正确性、画质和长稳状态是否明确，而非从附件存在推断验证完成？
- 写入后的飞书文档是否已重新读取并核对资源和链接？
